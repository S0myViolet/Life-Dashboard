# Research notes: Chrome Extensions Manifest V3 (Chrome 140+). Stable on 2026-09-23 is mostly Chrome 153, with 154 and 155 in partial rollout. Covers alarms, service worker lifetime, tabs/windows/scripting, content scripts and messaging, CORS, storage, badge, notifications, loading unpacked and remote code. Verified.

_Collected 2026-09-24 via web research (verified by a second pass). Sources are linked per fact. The build container itself cannot reach these hosts._

## Corrections and surprises

- CORRECTED (stable version): versionhistory.googleapis.com shows Windows stable on 2026-09-23 as 153.0.8010.53 at about 79%, 154.0.8037.57 at about 10% and 155.0.8059.12 at about 0.5%. - CORRECTED (alarm persistence): the earlier surprise said to treat 'alarms may be cleared on restart' as outdated. That overstates it. The Chrome 137 start version was not re-fetched.
- CORRECTED (extension key): the only key-generation method in the official docs is Chrome Developer Dashboard > Package > 'View public key'. The pack-and-copy and openssl methods are not in the official docs.
- ADDED (service worker keepalive): the lifecycle page also lists Chrome 109 ('Messages sent from an offscreen document reset the timers') and Chrome 114 ('Sending a message using long-lived messaging keeps the service worker alive'). It also lists Chrome 116 longer timeouts for permissions.request(), identity.launchWebAuthFlow() and similar calls.
- Upgraded to verified-official-doc: the 500-alarm limit (Chrome 117), the 1-minute to 30-second change (Chrome 120), the service worker 30s/5min/fetch-30s rules, top-level listener registration, the CSP allowed values including unpacked-only localhost, host_permissions, the content_scripts keys and content-script API access, CORS in network requests, and the rule that runtime.sendMessage cannot reach content scripts. - runtime.onMessage promise return: comparing chrome-types releases shows the IDL return type switching to '(boolean | Promise<any>) | undefined' between the 2025-12-17 and 2026-01-12 trunk builds, around M145/M146. That fits the '146' extract better than '148', but the shipping version is still unverified.
- message_serialization is confirmed in Chromium source as a stable-channel MV3 manifest key with values 'structured_clone' or 'json'. The Chrome 148 version is unverified.
- Unverified and left as is: that clicking reload on an unpacked extension fires onInstalled with reason 'update'. runtime_api.cc sets 'update' whenever a valid previous version exists, but the reload path was not traced. Also unverified: that open DevTools keeps the service worker alive, the Chrome 133 Energy Saver freezing, and that declaring devtools_page turns off the browser namespace.

### The minimum chrome.alarms delay and period is 30 seconds (0.5 minutes). Smaller values are not honored and log a warning. Alarms can also fire later than scheduled by an arbitrary amount. **(load-bearing)**

### Alarms persist across browser restarts by default in Chrome. persistAcrossSessions was added in Chrome 150 and defaults to true in Chrome. The alarms page prose still says persistence is not guaranteed, so re-create alarms on startup. **(load-bearing)**

IDL (chrome-types and chromium alarms.webidl): 'Whether the alarm should persist across sessions (browser restarts). In Chrome, this defaults to true to match historical behavior, but you should set this explicitly to maximize compatibility across browsers.' Tagged @since Chrome 150. Alarms page prose from the mirror snapshot, whose date is unknown and which has no Chrome 150 annotations: 'Alarms generally persist until an extension is updated. However, this is not guaranteed, and alarms may be cleared when the browser is restarted. Consequently, consider setting a value in storage when an alarm is created, and then ensure it exists each time your service worker starts up.' MDN PR mdn/content#45712 ('[WebExtensions] alarms.create() argument persistAcrossSessons') is still OPEN: created 2026-09-14, last updated 2026-09-21, not merged. It describes true as persisting until the extension updates, and false as cleared on extension reload or update or browser restart. It says 'As of September 2026, only Chrome 150+ supports this attribute', and that Firefox may default to false. Recommended pattern: pass persistAcrossSessions: true explicitly. In both runtime.onInstalled and runtime.onStartup, call chrome.alarms.get(name) and recreate the alarm if it is missing.

### While the device sleeps, alarms do not wake it. On wake, missed alarms fire, and a repeating alarm fires at most once before being rescheduled from the wake time. **(load-bearing)**

Verbatim from a mirror snapshot of the official alarms page: 'Alarms continue to run while a device is sleeping. However, an alarm will not wake up a device. When the device wakes up, any missed alarms will fire. Repeating alarms will fire at most once and then be rescheduled using the specified period starting from when the device wakes, not taking into account any time that has already elapsed since the alarm was originally set to run.' The older Google source said: 'The behavior of alarms when a device goes to sleep is currently undefined. An alarm will never fire early but may fire significantly later than expected if a device went to sleep after an alarm was scheduled.'

### An extension service worker stops after 30 seconds of inactivity. Receiving an event or calling an extension API resets that timer. It is also stopped if a single event or API call takes more than 5 minutes, or if a fetch() response takes more than 30 seconds to arrive. **(load-bearing)**

Verbatim from the lifecycle page source (published 2023-05-02, updated 2023-09-27): 'After 30 seconds of inactivity. Receiving an event or calling an extension API resets this timer.' / 'When a single request, such as an event or API call, takes longer than 5 minutes to process.' / 'When a fetch() response takes more than 30 seconds to arrive.' / 'Chrome 110: Extension API calls reset the timers. Before this, only running event handlers would keep a service worker alive.' Blog 'longer-esw-lifetimes' (2023-01-27): 'Starting in Chrome 110 ... extension service workers stay alive as long as they're receiving events' and 'the idle timeout will not occur if there are pending events'. Global variables are lost on shutdown. Persist state with chrome.storage, IndexedDB or CacheStorage.

Source: https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/extensions/mv3/service_workers/service-worker-lifecycle/index.md ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/blog/longer-esw-lifetimes/index.md · confidence: verified-official-doc

### Service worker event listeners must be registered synchronously at the top level of the script. **(load-bearing)**

Verbatim from Google's doc source: 'Event handlers in service workers need to be declared in the global scope, meaning they should be at the top level of the script and not be nested inside functions. This ensures that they are registered synchronously on initial script execution, which enables Chrome to dispatch events to the service worker as soon as it starts.' So call chrome.alarms.onAlarm.addListener, chrome.runtime.onMessage.addListener and similar at module top level, never after an await.

Source: https://developer.chrome.com/docs/extensions/get-started/tutorial/service-worker-events ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/extensions/mv3/service_workers/events/index.md · confidence: verified-official-doc

### Manifest content_scripts entries use "matches" (required), "js", "css", "run_at", "all_frames" and "world". run_at is 'document_start' | 'document_end' | 'document_idle', and the default is document_idle. **(load-bearing)**

### fetch() from the extension service worker can reach remote servers without CORS headers from the server, as long as the host is in host_permissions. Content scripts are always subject to CORS as the page's origin, even with host permissions. **(load-bearing)**

Doc source (updated 2023-07-13): 'Each running extension exists within its own separate security origin. Without requesting additional privileges, the extension can call fetch() to get resources within its installation.' To reach remote servers, add hosts or match patterns to host_permissions. 'Content scripts initiate requests on behalf of the web origin that the content script has been injected into and therefore content scripts are also subject to the same origin policy.' 'Content scripts have been subject to CORB since Chrome 73 and CORS since Chrome 83.' The doc recommends that the service worker validate and build the cross-origin request, with the content script supplying only data. Pattern: the content script sends data to the service worker, which calls fetch('https://<dashboard>/api/ingest', {method:'POST', headers:{'Content-Type':'application/json', Authorization:'Bearer <token>'}, body}). If the host is not in host_permissions, the server must answer CORS for Origin chrome-extension://<id>. Exactly which Origin header is sent was not verified.

Source: https://developer.chrome.com/docs/extensions/develop/concepts/network-requests ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/extensions/mv3/network-requests/index.md · confidence: verified-official-doc

### chrome.storage quotas: local is 10485760 bytes (10 MB), or unlimited with the "unlimitedStorage" permission. session is 10485760 bytes, held in memory only, and by default only extension pages and the service worker can access it. sync is 102400 bytes total, 8192 per item, 512 items, 120 writes per minute and 1800 per hour. **(load-bearing)**

Constants: chrome.storage.local.QUOTA_BYTES = 10485760 ('This value will be ignored if the extension has the `unlimitedStorage` permission'). chrome.storage.session.QUOTA_BYTES = 10485760 ('stored in-memory and will not be persisted to disk', Chrome 102+, MV3 only). setAccessLevel doc: 'By default, `session` storage is restricted to trusted contexts (extension pages and service workers), while `managed`, `local`, and `sync` storage allow access from both trusted and untrusted contexts.' Content scripts can read storage.session only after setAccessLevel({accessLevel:'TRUSTED_AND_UNTRUSTED_CONTEXTS'}). Exceeding a quota rejects the promise or sets runtime.lastError. Permission: "storage". getKeys() is Chrome 130+. Event: onChanged(changes, areaName). sync.MAX_SUSTAINED_WRITE_OPERATIONS_PER_MINUTE is deprecated.

Source: https://developer.chrome.com/docs/extensions/reference/api/storage · confidence: verified-official-doc

### chrome.notifications.create(id?, options) returns Promise<string>. It requires the "notifications" permission, and type, iconUrl, title and message are required.

TemplateType: 'basic' | 'image' | 'list' | 'progress'. iconUrl may be a data URL, blob URL, or path inside the extension package. Options: requireInteraction (Chrome 50+), silent (Chrome 70+), buttons (at most 2), priority from -2 to 2 (-2 and -1 raise an error on Windows, Linux and Mac), eventTime, progress 0-100. ### An unpacked extension's ID comes from its folder path and changes if it is loaded from a different directory. Adding a "key" (public key) to manifest.json pins the ID. **(load-bearing)**

Verbatim, from a fork of the Google doc source (architecture overview): 'the ID of an unpacked extension will change if the extension is loaded from a different directory; the ID will change again when the extension is packaged.' The 'key' manifest doc: 'This value maintains the unique ID of an extension, or theme when it is loaded during development.' Official way to get a key (Google doc source partial reusing-prod-extension-id.md): upload a .zip to the Chrome Developer Dashboard without publishing, open Package > 'View public key', copy the text between '-----BEGIN PUBLIC KEY-----' and '-----END PUBLIC KEY-----', remove the newlines, and set it as "key" in manifest.json. Then check that chrome://extensions shows the same ID as the Dashboard Item ID. These methods are not in official docs: packing locally and copying "key" from <profile>/Extensions/<id>/<ver>/manifest.json, and generating an RSA key with openssl and base64-encoding the DER SPKI public key. A stable ID matters if the dashboard allowlists Origin chrome-extension://<id> for CORS, or uses externally_connectable.

### MV3 blocks remote code execution in extension pages and the service worker. The CSP floor is "script-src 'self' 'wasm-unsafe-eval'; object-src 'self';". script-src, object-src and worker-src may only contain 'self', 'none' and 'wasm-unsafe-eval', plus any localhost source for unpacked extensions only. **(load-bearing)**

Doc source (manifest CSP): minimum policy "content_security_policy": { "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self';" }. Verbatim: 'The `extension_pages` policy cannot be relaxed beyond this minimum value. In other words, you cannot add other script sources to directives, such as adding `'unsafe-eval'` to `script-src`.' Doc source (migrating/improve-security): allowed values for script-src, object-src and worker-src are self, none, wasm-unsafe-eval and, for unpacked extensions only, 'any localhost source, (`http://localhost`, `http://127.0.0.1`, or any port on those domains)'. The manifest key is a dictionary: { "extension_pages": "...", "sandbox": "..." }. eval and new Function work only in sandboxed pages. Fetching JSON data at runtime is fine. The Web Store remote-code policy does not apply to a private unpacked extension, but the browser enforces the CSP regardless, so bundle all JS, e.g. with Vite or esbuild.

Source: https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/extensions/mv3/manifest/content_security_policy/index.md ; https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/extensions/migrating/improve-security/index.md · confidence: verified-official-doc

### Background or minimized collector tabs are subject to page throttling. Chained timers in pages hidden for more than 5 minutes run about once a minute (Chrome 88+). With Energy Saver on, CPU-intensive hidden tabs can be frozen (Chrome 133+). Tabs can also be discarded.

Intensive throttling applies when the page has been hidden more than 5 minutes, silent at least 30 seconds, WebRTC is not in use, and the timer chain count is 5 or more. Energy Saver freezing applies after more than 5 minutes hidden and silent, and a frozen tab unfreezes on activation. Mitigations: drive collection from chrome.alarms in the service worker, tabs.update({autoDiscardable:false}), and check tab.frozen / tab.discarded. Whether a tab in a minimized window reports visibilityState 'hidden' was not verified; it is likely on most platforms. [Verifier: the Chrome 88 intensive-throttling conditions and the once-per-minute interval match the Google doc source verbatim. The Energy Saver freezing post (Chrome 133) is not in the archived repo and was not re-verified.]
