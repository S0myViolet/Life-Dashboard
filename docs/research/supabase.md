# Research notes: Supabase (current docs, re-verified 2026-09-24): Edge Functions, keys/JWT, pg_cron scheduling, auth.uid()/auth.jwt(), pooler + RLS from serverless, billing/backups, Storage RLS, Next.js SSR + Google auth

_Collected 2026-09-24 via web research (verified by a second pass). Sources are linked per fact. The build container itself cannot reach these hosts._

## Corrections and surprises

- CORRECTED: the Edge auth doc says `auth: 'secret'` validates "against any secret key from your dashboard", but @supabase/server 1.8.0 (docs/auth-modes.md and dist code `keyName ?? "default"`) matches only the secret key NAMED 'default'. Use `auth: 'secret:*'` to accept any secret key, or `auth: 'secret:<name>'` for a dedicated cron key. Otherwise a cron-only function will reject a non-default key.
- NEW: @supabase/server rejects legacy anon/service_role keys and legacy HS256 user JWTs. 'user' mode needs a `kid` in the JWT header, so a project must be migrated to asymmetric JWT signing keys (ES256/RS256) before withSupabase({ auth: 'user' }) works.
- CORRECTED: the earlier surprise said 'the docs now say not to read keys from env inside Edge Functions'. No such statement was found. secrets.mdx still shows JSON.parse(Deno.env.get('SUPABASE_SECRET_KEYS')!)['default']. What api-keys.mdx does say is to use the @supabase/server SDK 'rather than relying on the platform [verify_jwt] check', because verify_jwt alone does not authenticate API-key-only callers.
- CORRECTED: Supabase's RLS/testing docs set `set local request.jwt.claim.sub = '<uuid>'`, not `request.jwt.claims`. That makes auth.uid() work, but auth.jwt() stays NULL (it reads only request.jwt.claim / request.jwt.claims). So Storage-style policies using `(select auth.jwt()->>'sub')` fail under that test pattern. Use set_config('request.jwt.claims', '<json>', true) in a local shim.
- CORRECTED: signing-keys.mdx says you 'must disable the anon and service_role' keys BEFORE revoking the legacy JWT secret. It does not say revocation invalidates them automatically. The legacy-key timeline (restored from 1 Nov 2025 without legacy keys; deletion late 2026 TBC) exists only in GitHub discussion #29260. The docs pages give no dates, so the confidence is lowered to secondary-source.
- CORRECTED source: the /tmp ephemeral storage limits (Free 256MB / Paid 512MB, reset per invocation) come from guides/functions/ephemeral-storage.mdx, not limits.mdx. The auth.uid() EXPLAIN output is in the RLS performance troubleshooting doc, not the RLS guide.
- CORRECTED detail: background-tasks.mdx contains no type import. The CLI 2.117.0 function template uses `import "@supabase/functions-js/edge-runtime.d.ts"` with deno.json mapping "@supabase/functions-js": "jsr:@supabase/functions-js@^2". The claim that troubleshooting docs say waitUntil does not extend wall-clock is unverified.
- CORRECTED detail: the compute example bill in the docs uses Small compute ($25 + $15 - $10 = $30). The roughly $25/month figure for one Micro project on Pro is an inference.
- The egress proxy blocks supabase.com, and the GitHub MCP is restricted to the user's repo, so every doc fact was re-read from raw.githubusercontent.com Markdown sources via WebFetch (a summarizing model; code blocks were requested verbatim). Package facts (auth-js, storage-js, ssr, server, functions-js, drizzle-orm, CLI binary strings) were checked directly in npm tarballs. The WebSearch budget for the session was exhausted, so no new search-based discovery was done.
- The Edge Function scheduling doc no longer uses 'Authorization: Bearer <anon key>'. It sends the publishable key on 'apikey', with Vault secrets named 'project_url' and 'publishable_key'. A publishable key plus the platform's verify_jwt check does not authenticate the caller. For a cron-only function, send a SECRET key on apikey, set verify_jwt = false, and check it with withSupabase({ auth: 'secret:*' }) (or 'secret:<name>').
- The new sb_publishable_/sb_secret_ keys are not JWTs and cannot go in Authorization: Bearer. Secret keys return 401 when the User-Agent looks like a browser. Designs that rely on SUPABASE_ANON_KEY / SUPABASE_SERVICE_ROLE_KEY or the legacy JWT secret are at risk because of the planned late-2026 removal.
- The Next.js docs use lib/supabase/{client,server,proxy}.ts and a root proxy.ts exporting `proxy` (Next 16), with env var NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY. The OAuth PKCE partial still imports '@/utils/supabase/server' and uses redirectTo `http://example.com/auth/callback`, so the docs are inconsistent. In @supabase/ssr 0.12.7, setAll receives a second 'headers' argument (Cache-Control/Expires/Pragma) that the proxy must copy onto the response. It is delivered only on a server client's first cookie write, so create a new client per request.
- The docs contradict each other on static files. The WASM doc says 'Static files cannot be deployed using the `--use-api` API flag', while CLI SIDE_EFFECTS.md says API deploys record `static_patterns`. Discussion #32815 users report static files silently not uploading with --use-api or without Docker. function-configuration.mdx does not document static_files at all.
- CLI 2.116.0 broke local Edge Runtime startup for monorepo imports outside supabase/functions because of overlapping Docker bind mounts (issue #50088, closed, fixed via supabase/cli#6505). API-mode deploys in the TS CLI only upload imports inside the nearest git root. Docker bundling mounts import-map `scopes` targets even outside the git root, with a WARN.
- The npm package supabase@2.117.0 is a thin wrapper around platform packages (for example @supabase/cli-linux-x64), which ship two binaries: `supabase` (TS) and `supabase-go` (Go sidecar).
- The Drizzle RLS example builds claims from getSession() plus an unverified decode and interpolates them with sql.raw. Verify the token with auth.getClaims() first, then allow-list the role and escape or parameterize the values. The Drizzle docs main branch also now says to install drizzle-orm@rc (1.0.0-rc.4), while npm latest is 0.45.3.
- The Supabase Auth migration marks auth.uid(), auth.role() and auth.email() as 'Deprecated. Use auth.jwt() -> ''sub'' instead.' The Storage docs now write policies with (select auth.jwt()->>'sub') and add the operation-aware helpers storage.allow_only_operation() / storage.allow_any_operation().
- The Edge Function wall-clock limit (150s Free / 400s paid) is how long a worker stays alive, not a per-request limit. CPU time is 2s per request. The request idle timeout (150s, then a 504) applies separately. Memory is 256MB. pg_net is rated for about 200 requests/second.

### Q5: supabase.auth.getClaims(jwt?, { allowExpired?, jwks? }) checks the JWT locally with WebCrypto against a cached JWKS when the token is asymmetric. For HS* tokens, tokens without a kid, kids not found in the JWKS, or runtimes without WebCrypto, it calls getUser() on the server. **(load-bearing)**

Checked in @supabase/auth-js@2.117.1, src/GoTrueClient.ts (line ~6690). Return type: { data: { claims: JwtPayload; header: JwtHeader; signature: Uint8Array }, error: null } | { data: null; error: AuthError } | { data: null; error: null }. Fallback: `!header.alg || header.alg.startsWith('HS') || !header.kid || !('crypto' in globalThis && 'subtle' in globalThis.crypto) ? null : await this.fetchJwk(...)`. fetchJwk also returns null when the kid is not in the fetched JWKS.
